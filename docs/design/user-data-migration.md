# 从旧 App 备份迁入用户数据（#39 关口 6）

依据：[ADR 0003](../adr/0003-native-worker-with-project-linux.md)，[#39](https://github.com/lvivvde/deepseek-harness-ipad/issues/39) 关口 6。2026-10-08 创建。

## 规则

新架构不挂载旧 App 的 ext4 用户盘 `user.raw`，唯一的输入是旧 App 导出的完整备份 `HarnessBackup.tar` 和它的 `.sha256` 校验文件。所以旧盘不会被两个执行器同时写：新架构从不写它（演练只以只读方式读取它的大小和摘要），旧盘始终只有旧 App 的 Linux 在写。覆盖安装回旧包后，旧数据和旧 App 照常可用：演练以旧包启动到 `ready`，加上迁移前后旧盘不变，来证明这一点。

`UserDataMigrator`（`ios/HarnessApp/Sources/Migration/`）的步骤：

1. 拿锁（`flock`，进程死亡即释放），校验摘要，检查空间。
2. 先给所有条目做计划和哈希，再写任何东西。只差大小写或 Unicode 规范化的同名冲突一律拒绝（`NAME_CONFLICT`），不合并。冲突时整份备份都不迁移，用户先在旧 App 里改名，再重新导出。
3. 在目标旁边的暂存目录展开，再按清单从磁盘逐文件核对 SHA256、mode、symlink 和硬链接。
4. 迁移官方会话：zstd 解压为明文，`cwd` 从 `/root/projects` 改为 `/dsh/workspace`，会话目录重新编键。这一步在暂存目录里完成，所以早于切换；被杀时同样不影响目标。
5. 写标记 `.migration.json`（含归档摘要），然后用一次 rename 切换到目标。

另外：
- 凭据、缓存和特殊文件（FIFO、socket、设备）只报告、不迁移。凭据由用户重新输入。特殊文件由 `MigrationTests` 覆盖，因为旧导出器不会产生它们。
- 在 rename 之前，任何失败或进程被杀都不改动目标。下次运行会清理残留的暂存目录，然后重新开始。
- 用同一份备份再次运行，结果是 `alreadyMigrated`，不会覆盖迁移之后的修改。目标已存在而备份不同时，结果是 `TARGET_EXISTS`。

## 回退演练

演练 App（`ios/HarnessApp/scripts/gate6/drill/`）用专用测试 bundle ID `org.lvivvde.harness.g6drill`。旧包是正式 App 的 7956e8c 构建，改为同一个测试 ID 后重签，所以新旧两个包共用一个容器。

正式 Harness 和 LinuxPrototype 不参与演练，它们的容器也不动。

步骤：

1. 装旧包并启动，等到 `ready` 后停止。
2. 推入合成备份，覆盖安装新包，然后迁移：
   - 目标与预期清单逐项一致；
   - 迁移前后旧盘不变；
   - 写入一处迁移之后的修改。
3. 覆盖安装回旧包，启动到 `ready`。
4. 再覆盖安装新包，第二次运行，要求：
   - 结果是 `already`；
   - 标记不变；
   - 迁移后的修改仍在。

旧盘的身份包括：大小、inode、mtime、ctime，以及数据区的 SHA256。

ctime 在任何写入时都会变化，用户空间无法回拨。

`user.raw` 是 8 GB 的稀疏文件，实际数据约 40 MB。整读这个文件时，在 4 GB 之后停住超过 15 分钟。所以演练只哈希数据区（`SEEK_DATA`/`SEEK_HOLE`），每段连同偏移和长度一起计入摘要，空洞由文件大小隐含。

演练第一次运行时是从头整读，结果卡住了。

## 证据

- **macOS / Lima 合成矩阵 34/34**（`scripts/gate6/synthetic-matrix.py`）。备份由旧 App 自己的导出器生成，在 macOS 和大小写敏感的 ext4 上分别导出，使用 guest 镜像里的 node 和 node-tar。覆盖：
  - 两平台迁移结果与预期一致，清单相同，重跑是空操作；
  - 大小写冲突和 Unicode 冲突被拒绝；
  - 摘要不符、校验文件无效、归档截断、头部损坏、空间不足（预检和写入中 ENOSPC），以及在 10 个阶段分别被杀。这些情况下目标都保持原状，重试可以成功；
  - 第二个进程报 `MIGRATION_BUSY`；
  - 已有目标不会被覆盖；
  - 迁移后的修改得到保留；
  - 每次运行后源归档都不变（Mac 上没有旧盘，用源归档代替它）。
- **iPad 回退演练**（2026-10-08，真机）。合成备份由旧导出器在 Mac 上生成，再推入演练 App 的容器：
  - 旧包两次启动都到 `ready`。
  - 第一次迁移 7/7：14 个文件、24 个目录、2 个 symlink、1 组硬链接、2 个会话（解压 1 个，移动 1 个），排除凭据 4 项、缓存 2 项，与预期清单零差异，旧盘不变，没有残留暂存目录。
  - 回退后再升级 7/7：`already`，标记和迁移后的修改都在。旧 App 在回退期间改写过自己的盘，这本来就应该发生，迁移不受影响。
- **iPad 被杀矩阵 10/10**（真机，与 Mac 矩阵同样的 10 个阶段）。每个阶段在演练 App 里迁移到一个新目标，到点时进程向自己发 SIGKILL；再由新进程重试，然后再跑一次。每个阶段都满足：
  - 被杀后目标不存在；只有在 `switched` 被杀时，目标已完整切换并带有标记；
  - 重试得到 `migrated`（`switched` 时为 `already`），再跑一次是 `already`，报告相同；
  - 与预期清单零差异，标记与第一次演练的相同，没有残留暂存目录，旧盘不变。

  演练 App 是多线程的，向自己发出的 SIGKILL 不会立刻停住当前线程。第一轮在 `switching` 被杀时，rename 抢先完成了，重试于是得到 `already`。现在故障钩子发出信号后会一直阻塞，不再回到迁移器；修好后整轮重跑。这是演练本身的缺陷，迁移器没有改动。
- **iPad 名字冲突 2/2**（真机）：大小写冲突和 Unicode 冲突的备份在 ext4 上由旧导出器生成，在 iPad 容器里都被整份拒绝（`NAME_CONFLICT`），没有目标，也没有残留暂存目录。同时探测了这个卷：iPad 容器区分大小写，但不区分 Unicode 规范化形式。所以 Unicode 冲突在 iPad 上确实会撞名，大小写冲突的拒绝是保守做法，好处是同一份备份在任何卷上都得到同一个结论。
- **真实备份 5/5**：由用户在 iPad 上经“文件”App 从正式 App 导出，并在演练 App 里选择，不经过 Mac。演练 App 迁移到临时目录、再跑一次确认是空操作、然后删除解出的内容。收据只记计数、摘要和结论。
  - 归档约 0.65 MB，`migrated`：73 个文件、62 个目录，共约 0.5 MB。
  - 8 个会话全部解压，3 个移入工作区路径，5 个不属于任何项目。
  - 排除凭据 1 项、缓存 10 项，没有特殊文件。
  - 第二次运行 `already`，报告完全相同；解出的内容已删除。
  - 选错文件时会以固定错误码拒绝：只选一个文件时是 `SELECTION_NEEDS_TAR_AND_SHA256`，选到不是完整备份的小归档时是 `LAYOUT_INVALID`。这时收据只记录归档结构（条目类型计数和顶层分类），不记录名字。

正式 App 的升级和真实迁移不在本关口内。
