# 会话检查点与恢复：设计讨论

状态：2026-10-11，用户已确认以下共同理解；实现位于 `codex/session-recovery`，基于终端分支 `4bc2b21`。下文记录已选设计与验收合同。

## 已确认行为

- 已有会话的检查点损坏且没有可用副本时，保留数据并显示诊断，停止恢复。只有用户明确选择后才新建空会话。
- 保存失败时允许当前会话继续，持续显示“尚未保存”，并重试保存；不得把内存中的内容标成已耐久保存。
- 恢复信息按项目汇总显示：工作区相对检查点有变化、有结果未知的调用、有保留草稿。本轮不要求精确关联会话中的具体工具调用。
- 沿用 ADR 0003 与工作区耐久规则：工作区保持实际内容、不回滚；没有完成记录的工具调用为结果未知、不重放；草稿保留。
- Worker home 保持全局范围，只保存 home，不含项目文件、草稿或凭据。项目的恢复状态各自维护，不承诺跨文件事务。

## 当前证据

- `runtime/candidate/candidate-bridge.js` 的检查点文件条目使用 `base64`；`CandidateHostTests.swift` 的夹具使用 `data` 且只核对路径。需要真实 Worker → Swift 保存 → Worker 恢复的字节往返验证。
- `CandidateHost` 独立替换根目录下的 `worker-home.json`，没有保留上一份、校验封装或专门的损坏隔离；读取失败与文件不存在都可能返回空检查点。
- 官方持久化 flush 在候选 Worker 中只把已接收事件写进内存 VFS；Swift 耐久保存的确认才代表原生存储完成。现有桥接没有检查返回的 `durable: true`。
- 当前保存失败只有会被后续事件覆盖的 Worker 事件文字，不是持续的保存状态。
- 每个已打开项目已有代际、草稿和未知调用恢复记录；尚未打开的项目没有活跃网关。调用账本的操作 id 尚未关联官方会话或其中的具体工具调用。
- 官方会话的起始目录可用，但不是所有工具实际操作项目的完整记录。不能凭它猜测恢复信息归属。

证据来自限定范围的源码核查；知识图谱工具不可用，generation 与 coverage 未知。架构扫描时现有 Swift 宿主/候选回归和 15 项桥接测试通过；它们不覆盖完整恢复合同。

## 三种 interface 的比较

| 设计 | 调用方需要知道什么 | depth 与 locality | 取舍 |
| --- | --- | --- | --- |
| A：协调 module | 恢复、请求保存、读取状态 | 采集顺序、耐久确认与恢复集中，调用方得到更多 leverage | implementation 跨 Worker 和 Swift，需共同合同测试 |
| B：显式采集票据 | begin、flush、采集、commit、票据和修订号 | 封装与存储有 locality，调用方的 interface 较宽 | 当前只有一个主要采集入口，公开这些细节收益不足 |
| C：原生主动请求采集 | Worker 报告变化并回答原生请求 | UI 与调度集中在 Swift | 需新增推送请求、响应和失联处理流程 |

推荐 A，把 B 的不可变封装、原生签发采集标记与 C 的持续保存状态收进 implementation。暂不新增原生主动采集流程，也不公开票据的顺序规则。删除这个 module 会把验证、顺序与恢复知识重新分散到调用方；只把现有桥接拆成多个 shallow module 不会增加 depth。

## 推荐 module 与 seam

逻辑上的“会话检查点与恢复”是一个 deep module，跨两种语言共同拥有 implementation：

- Worker 部分封装官方持久化 flush、home 采集和恢复、事件合并、周期保存及失败重试。官方启动的 restore/install 两个挂接点保持现有顺序，由启动 adapter 接入 module。
- Swift 部分封装检查点格式验证、耐久存储、恢复选择、采集基线和持久可见的保存状态。`CandidateHost` 只把相应原生请求交给它。
- 原生 UI 读取专门的会话保存/恢复状态。它不解释检查点文件或 Worker 日志，后续 Linux、终端或 Worker 事件也不能覆盖保存失败状态。

调用方的概念 interface 如下，表示责任与行为，不锁定实现中的命名：

```text
恢复会话 → 首次初始化 / 恢复完成及诊断 / 恢复受阻
请求保存 → 已耐久确认 / 保存失败；module 安排后续重试
读取状态 → 最后成功保存、正在保存、尚未保存、恢复受阻、项目提示
```

采集票据、Worker 身份与递增修订号属于内部 transport seam。它们用于拒绝旧 Worker 或过期采集的提交，以及防止迟到的确认把较新变化标成已保存；调用方不用维护这些规则。

文件和 VFS 属于 local-substitutable 依赖。内部采用原生耐久文件与可注入故障的临时文件 adapter、真实 Worker VFS 与内存 VFS adapter；生产桥接和测试往返都执行同一个合同。保留现有 SwiftPM 目标，暂不为单一实现增加通用存储或调度抽象。

拟收拢的位置：Worker home 逻辑由 `runtime/candidate/candidate-bridge.js` 收进专属实现文件；Swift 从 `CandidateHost` 收进 `Sources/Candidate` 的恢复 module。`WorkspaceStore` 和 `ProjectGateway` 只补必要的项目恢复事实读取，不重复实现耐久写租约。

## 保存顺序与项目提示

一次采集严格按以下顺序执行：

1. Swift 分别在已打开项目现有的串行访问位置采集项目 id、代际和基线是否可用。原生签发不允许 Worker 修改的采集标记。
2. Worker 等官方会话 flush 完成，再采集 home 的完整内容。官方 flush 在当前 VFS 中只代表内存事件完成。
3. Swift 完整验证后保存不可变封装；home 与步骤 1 的项目代际引用放在同一封装中。这里的项目元数据不是项目文件、草稿或调用结果字节。
4. 只有文件和目录同步成功、收到匹配的耐久确认，才确认这一修订已保存。保存期间新增的活动仍为未保存，随后再采集一次。

项目之间分别采样，不承诺同一瞬间的跨项目事务。保存期间发生的变化也可能产生保守提示，显示为“工作区在此保存期间或之后有变化”；不得在采集 home 后补采较新的代际以消除提示。

项目恢复提示在该项目正常打开后，读取其真实耐久状态再计算。没有记录基线的项目、合法旧检查点中的项目或恢复记录有缺口的项目，显示无法比较，不报告“没有变化”。恢复不会为获取提示而预热其他项目的 Linux。

结果未知与草稿是当前项目事实，按项目汇总，不假定它们只发生在检查点之后，也不从会话起始目录推断归属。本轮不输出“检查点后已完成调用”的精确列表，不整理调用账本，因此无需以代际替代调用完成游标。保留所有未知调用与原有账本；不得调用现有 `.checkpoint` 清理逻辑删除 UNKNOWN。后续若要整理账本或精确列出已完成调用，必须另用调用完成顺序，不能仅靠代际。

## 完整检查点、旧格式与新建

推荐保留当前及上一份经过验证的完整检查点。封装记录版本、检查点身份、修订号、home 内容、项目代际引用与完整性校验。先完整校验所有条目，再向 VFS 注入，避免在部分恢复的 home 上启动会话。

- 验证字段类型、完整 base64、路径、重复条目与文件/目录关系；排除项目、草稿和凭据，不能接受测试夹具的 `data` 作为生产字段替代品。
- 当前副本损坏但上一份完整时，恢复上一份，持续显示回退诊断与保存时间，说明较新的会话内容未恢复。
- 无完整可用副本时，执行已确认的阻止恢复行为。未知的新版本格式、读取权限失败也不能当作首次启动。
- 损坏副本保存在隔离区；隔离失败时保留源文件并报告失败，不能通过删除证据继续。
- 独立的初始化记录区分首次没有检查点与已使用后的检查点丢失。初始化记录也走耐久写入；已有记录但缺少所有副本时，恢复受阻。
- 合法旧 `worker-home.json` 经过完整生产格式验证后可恢复。旧格式没有项目基线，明确报告无法比较；下一次成功保存写入新格式，在新格式经过验证前保留旧文件，不覆盖唯一有效副本。
- 用户明确选择新建时，保留旧文件和诊断，初始化新的全局 home。原生工作区、草稿、写者未知租约及调用记录不被清空，不派发任何命令。

替换过程中崩溃可留下旧副本或一份完整的新副本。重开依完整性和序号选择可用检查点，不把一次失败的写入确认补记成成功，也不回放工具调用。

## 保存进度与重试

推荐沿用当前事件合并 1.5 秒、周期检查 30 秒的节奏，串行并合并重复保存请求。失败保留当前内存会话和上一份完整检查点；持续显示“尚未保存”及最后一次成功保存时间，自动重试并提供手动重试。

官方明确要求 flush 时，应等到原生耐久保存完成或得到失败；仅完成内存 flush 不显示为保存完成。页面刷新或进入后台时尝试立即保存，但不能承诺系统强制结束前完成，也不能把周期 30 秒描述为严格的数据丢失上限。已有失败状态一直保留，直到较新的采集得到耐久确认。

## 验证计划

module 的 interface 是测试面；测试断言可见结果，内部重构不应迫使测试重写。

| 场景 | 必须验证的结果 |
| --- | --- |
| 真实 Worker → Swift → Worker 往返 | 文本与二进制字节、模式与必要元数据一致，使用生产 base64 合同 |
| 非法或越界条目、凭据、重复项、错误编码 | 保存或恢复被拒，VFS 不以部分恢复状态启动 |
| 当前副本损坏、所有副本损坏、读取失败 | 回退时诊断持续；没有可用副本则受阻；不自动新建 |
| 合法旧格式与未来格式 | 旧文件保留到新保存验证完成；未来格式受阻 |
| 保存各阶段失败、崩溃、重开 | 有完整副本可选，失败状态真实，损坏证据保留 |
| 保存期间新增事件、旧 Worker 迟到、旧确认迟到 | 新变化不被清成已保存，过期采集不覆盖新检查点 |
| 项目在采集期间变化、项目无基线 | 保守提示或无法比较，不隐瞒变化 |
| 未知调用、持租约、草稿、新建会话 | 不重放、不自动释放、不回滚，草稿字节保持 |
| 官方 flush 与自动/手动重试 | 内存 flush 不冒充耐久确认；保存失败后允许继续并持续提示 |

以真实临时存储和故障注入覆盖耐久行为；至少一个往返测试运行真实官方 flush/VFS 路径和同一 Swift handler。替换只验证宿主路径或浅层转发的检查点测试，保留写租约与工作区恢复的有效行为测试。

实现后的必要检查：`make check`、`make test-candidate`、相关 Swift 恢复与宿主测试及受影响的工作区回归。macOS 结果不登记成 iPad 真机通过；真机验证另按既有验收流程记录。

## 实现记录

- Worker 的 `session-recovery.js` 收拢恢复、完整校验、官方 flush、home 采集、修订追踪与串行保存。官方 `session/flush` 等待匹配的原生耐久确认；所有 home VFS 变化也会标记未保存，凭据例外。
- Swift 的 `SessionRecovery` 保留 `home-current.json` 与 `home-previous.json`；封装版本 2，校验整个序列化 body 的 SHA256。body 保存 home、采集前项目基线、身份、序号、修订与时间。根目录隔离区保留损坏/新建前的证据。body 与初始化记录共用初始化身份，防止旧会话副本获选。
- `home-initialized.json` 记录已初始化或明确为空。首次初始化与用户明确新建使用空标记；成功保存后改为已初始化。空标记仍扫描新的完整副本，只跳过明确新建时已隔离的原始字节；新建决定与原诊断耐久保存，重载后仍显示。已初始化后缺失副本即受阻，不使用保留的旧格式冒充新版恢复。旧 `worker-home.json` 保留为迁移证据。
- 首次保存、迁移或新建后第一次保存替换两个槽，避免保留的旧会话高序号获选。后续保存先耐久写入选中的上一份，再替换当前并验证，最后保存初始化记录。未确认的完整新副本可在重启时恢复；不会补发此前保存的耐久确认。
- UI 独立显示保存状态、最后成功时间、回退/受阻诊断、手动保存和需明确确认的新建动作；项目提示只读取已打开项目。持有写租约、缺少基线或恢复有缺口时不能比较代际。
- 自动保存沿用 1.5 秒合并与 30 秒周期重试；页面隐藏/离开与原生 scene 进入非活动状态尝试立即保存。它们不保证系统强制结束前完成。
- `home-recovery-probe` 只供本机测试，使用合成临时根目录；禁止 Linux 启动和命令重放。测试运行真实固定 Worker VFS、模块加载器、Cordis、JSONL 持久化及同一 Swift handler。

验证与真机缺口以交接文件的最新记录为准。系统断电、iPad 强制结束与前后台的这一版行为尚未实测；macOS 的 SIGKILL 矩阵不能替代它们。
